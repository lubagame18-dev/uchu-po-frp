# Подтверждение оплаты и баллы ИИ

Аудит 15 ноября 2026: ЮKassa подтвердила три реальных успешных платежа по 30 ₽,
в PocketBase все три были `created`. Один заказ имел прежний тип `plan_single`,
два — `single_1`. Новый тип отсутствовал в фильтре webhook; обработчик HTTP
всегда отвечал 200 даже при ошибке начисления. Возврат с банка только перечитывал
профиль и сообщал об успехе без проверки платежа. API-проверки входа также
упирались в общий лимит десять запросов в минуту.

Платежи сверены напрямую с ЮKassa: succeeded, paid, RUB, точная сумма, совпадение
номера заказа, владельца и продукта, отсутствие возврата. Через атомарный
`apply_payment` восстановлены три урока в исходных двух кабинетах. Переноса
между кабинетами или повторного списания денег не было. Отдельный заказ на 400 ₽
отменён провайдером и не начислялся. Личные идентификаторы и ключи в отчёт не входят.

Теперь `/pay/status` проверяет только заказы вошедшего пользователя и сверяет
их с API провайдера. При возврате с банка, входе и фокусе сайта он начисляет
подтверждённые покупки без ожидания webhook. `pay=ok` сам по себе ничего не
начисляет и больше не показывает ложный успех. Новые заказы сохраняют ID
провайдера, номер заказа возвращается в URL. Старые заказы поддерживаются
ограниченным поиском. Ошибка webhook даёт 503 для повторной доставки.

Один полный урок за 30 ₽ включает отдельный запас **10 баллов только на доработки**.
Создание списывает один урок и никогда не уменьшает эти баллы. Ориентир — 2–3
обычные доработки на урок, без ограничения числа нажатий: общий запас можно
потратить на любые документы. Длинные тексты расходуют больше. Остаток хранится
на сервере, не в кэше. Нулевая плашка открывает покупку нажатием/Enter.

Баллы — бюджет себестоимости: вход считается в четыре раза дешевле выхода
по проверенному пиковому тарифу Flash. Один балл — 2 000 выходных эквивалентов.
На создание предусмотрен отдельный закрытый бюджет 120 000 эквивалентов,
на доработки новой покупки — 20 000. При создании первый резерв списывает один урок один раз;
закрытый комплект не позволяет продолжать выдавать правки за создание.
Заведомо отклонённый провайдером запрос с нулевым расходом возвращает резерв.

Официальные цены и курс зафиксированы в `economics.json`. Даже консервативная
оценка обоих бюджетов как выходящих токенов по пиковому тарифу, с резервом 15%
к курсу, даёт около 15,87 ₽. После условного резерва 10% на оплату/налог остаётся
около 11,13 ₽ до постоянных расходов. Это не гарантия общей прибыли: точный договор
эквайринга, хостинг, изображения и будущие цены сюда не включены. Цены и лимиты количества уроков сохранены. Для новых подписок на 50 уроков выделяются 500 баллов на правки и отдельный общий бюджет создания; прежние оплаченные остатки не уменьшаются.

Перед запросом к ИИ сервер атомарно резервирует верхнюю границу расхода:
UTF-8-размер входа с запасом на сообщения + ограниченный выход. Параллельные
запросы не могут взять один остаток дважды. После ответа возвращается разница
до фактического usage; возврат идемпотентен. Для неизвестного сетевого исхода
резерв сохраняется консервативно, чтобы не разрешать повторный бесплатный расход.
Оплаченные запросы используют фиксированную модель Flash, без платных поисковых
инструментов и нескольких генераций за один запрос. Учёт уроков независим.
Минимальный журнал резервов включён в выгрузку и удаление аккаунта, включая применение журнала удаления к восстановленной копии.

Миграция повышает лимит лишь проверки сессии; лимит попыток входа сохранён.
Остатки прежних оплаченных покупок и потраченные баллы не сбрасываются. Прежним покупкам добавляется отдельный бюджет создания один раз. Их прежний запас 80 000 эквивалентов остаётся: 40 баллов на такой урок.

Проверки: `deploy/pocketbase/test-integration.py`, `test-balances.py` с
`POCKETBASE_BROWSER=1`, `test-privacy.py`, `test-identities.py`, `test-pricing.cjs`,
`python3 deploy/check-site-deploy.py`. В браузере проверяется реальное начисление
из изолированного PocketBase при возврате без webhook, запрет чужого заказа,
повторное подтверждение, небольшие числа и покупка только с нулевой плашки.

Сервер сначала проверяется на закрытой копии живой БД, с зашифрованным бэкапом
и восстановлением из S3. Function обновляется с сохранением всего окружения.
Статика выкладывается через существующий workflow и проверяется по SHA-256.
