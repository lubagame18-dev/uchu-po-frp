## Политика сохранена владельцем; следующим вводится S3-ключ

В настоящем конструкторе оказалось возможно выбрать несколько конкретных
действий. Владелец объединил их в одно правило и после замечаний о «Включить»
вместо «Исключить» и GetBucketVersioning вместо ListBucketVersions сообщил «готово».
Это подтверждение действий владельца; фактические права API ещё не приняты.

Ожидаемое правило: Разрешить → **Включить пользователей** → **Выбрать пользователей**
→ uchu-backups (`aje866hr3pr2riq1plbp`), только пять действий:

```text
GetBucketAcl
GetBucketVersioning
ListBucket
GetObject
PutObject
```

Четыре отдельных ресурса:

```text
uchu-frp-backups
uchu-frp-backups/pocketbase/slot-0.age
uchu-frp-backups/pocketbase/slot-1.age
uchu-frp-backups/pocketbase/slot-2.age
```

«Все пользователи»/«Все действия», ListBucketVersions и условия не требуются.
Повторно создавать или сохранять правило не нужно. При ошибке доступа Codex
проверит конкретный ответ, не потребует editor/storage.editor на весь каталог.

## Повторный ввод: вставка в HTTPS-форму

Первый введённый вручную секрет сохранился по формату, но реальные подписанные
запросы ACL, versioning и list получили SignatureDoesNotMatch/403. Анонимный список
получил AccessDenied/403. Первый запуск backup.service завершился ошибкой; реальная
выгрузка и восстановление не приняты. Публичный health PocketBase остаётся 200.

По просьбе владельца при необходимости повторного ввода запущена временная
HTTPS-форма на accounts.uchu-po-frp.ru/private-backup-setup/. Секрет можно вставить
через Ctrl+V/контекстное меню. Личная ссылка передаётся владельцу отдельно, её
одноразовый токен не помещается в репозиторий, пульт, журналы или черновики.
Ссылка действует 30 минут, допускает до пяти проверок; после успешного сохранения
закрывается. Сервис слушает только loopback за Caddy. Публичная страница без
токена не принимает ключ; Origin и Host проверяются, iframe/кеш/внешние ресурсы
закрыты. Секрет передаётся непосредственно VPS по HTTPS, не через Sites.

**Теперь ключ сохраняется только после настоящих проверок подписанного доступа,
ACL, версионирования и запрета анонимного доступа.** При ошибке старый конфиг не
меняется; значение остаётся только в поле браузера для исправления. Ни запросы,
ни ошибки SDK с их содержимым не журналируются. После подтверждения Codex удаляет
временный маршрут и останавливает веб-форму; RuntimeMaxSec=1800 ограничивает процесс.
Вручную перепечатывать ключ в консоль больше не требуется.

Если секрет исходного статического ключа не сохранён и окно Яндекса закрыто,
восстановить его из кабинета нельзя. Тогда владелец создаёт новый статический
ключ того же сервисного аккаунта, сообщает только новый ID, а Codex открывает
форму для этого ID. Секрет ни при каком варианте не отправляется в чат.

Статус других ключей: Postbox SMTP AUTH и настоящее письмо подтверждены владельцем.
Google/Яндекс ID сохранены, но реальные OAuth-входы ещё не проверены. Факт
сохранения в приватном env не считается доказательством правильности секрета.

Роли `storage.editor`/`editor` на весь каталог и публичный доступ не нужны.
Не включать версионирование: скрытые старые версии нарушили бы ограничение объёма.
Оставить максимальный размер бакета 1 ГБ, если он уже задан. Фактические бесплатные
квоты общие с другими ресурсами биллинга; нулевой счёт не обещается.

## Что выполняет Codex

- Установка штатного Ubuntu-пакета `python3-boto3`; SDK использует проверку TLS,
  фиксированный https://storage.yandexcloud.net и явно заданный отдельный S3-ключ.
- Секрет хранится root:600 в `/etc/pocketbase/backup-s3.json`, отдельно от env
  приложения, SMTP и OAuth. В аргументы команд и логи не попадает.
- Отправка уже зашифрованного age-снимка; plaintext, симлинки, публичный файл,
  неподходящая директория, пустой/слишком большой архив отклоняются.
- До записи: проверка ACL, отсутствия версионирования/посторонних файлов;
  отдельный клиент без подписи должен получить 403 AccessDenied при запросе списка
  и существующих копий. После записи — такой же запрет чтения нового объекта.
  Таймаут, ошибка TLS, 404 или другой неожиданный ответ не считаются запретом.
  Политика доступа API-ключом не читается; произвольные разрешения другим субъектам
  этими запросами не проверяются. До включения владелец применяет ограниченную политику.
- Ровно три объекта `pocketbase/slot-0.age` ... `slot-2.age`; слот меняется по UTC-дню.
  Не более 200 МиБ каждый, всего до 600 МиБ текущих объектов. Повторный запуск
  в тот же день обновляет тот же слот. Другие объекты не удаляются.
- Полное повторное чтение ciphertext и сравнение SHA256 с локальной копией.
- После выдачи доступа: реальная загрузка, отдельная проверка восстановления
  загруженного архива и здоровья приложения. Ошибки доступа не маскируются успехом.
- Включение после локального снимка через Systemd ExecStartPost; локальная копия
  сохраняется при сетевой ошибке, PocketBase уже перезапущен до сетевой операции.

Нельзя ставить приёмку независимой копии до фактической проверки сервера и облака.
Отдельное хранение ключа `/etc/pocketbase/backup.agekey` у владельца ещё требует
защищённой передачи: в чат/публичный бакет/репозиторий этот ключ не помещать.
Копия без отдельного ключа не решает полную потерю VPS.

```sh

```
